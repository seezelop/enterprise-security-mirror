# Enterprise Security Mirror (ESM)

Defensive cybersecurity lab implementing a fictional enterprise network with HQ, three branches, OSPF, VLAN segmentation, nftables firewalls, a DMZ, and automated checks.

**Implemented:** ESC-001, Web Application Security. FastAPI HTTPS portal, controlled BOLA reproduction (performed locally during development), audit-log detection, remediation and an audit-telemetry blind-spot exercise.

**Planned, not deployed:** ESC-002 Identity & Privilege Abuse; ESC-003 Lateral Movement & Resilience. No Active Directory, production database, SIEM or separate IDS is deployed in ESC-001.

## ESC-002: Active Directory Identity & Privilege Abuse (planned)

ESC-002 will extend the completed Windows domain exercises in [blue-team-labs](https://github.com/seezelop/blue-team-labs/tree/main/labs/11-active-directory-security-events) and [Lab 12: Privilege Changes](https://github.com/seezelop/blue-team-labs/tree/main/labs/12-active-directory-privilege-changes).

**Architecture decision (2026-11-15):** use **Microsoft Windows Server 2022 Active Directory Domain Services (AD DS)** in a Linux-hosted **KVM/libvirt virtual machine**, connected to the existing Containerlab/Open vSwitch enterprise topology. Run **Wazuh using Docker** where host resources allow; use a Wazuh agent on Windows Server for native Windows Security events. **Samba AD DC is not the selected domain controller**: it is not a substitute for Microsoft AD DS, native Windows Security logs or full Windows GPO behavior.

Planned learning objectives: AD DS, DNS, Kerberos, LDAP, organizational units, groups, Group Policy, least privilege, Windows Security event correlation, detection with Wazuh/Python, MITRE ATT&CK mapping where supported, remediation and repeat testing. Security+ SY0-701 objectives include AAA, IAM, hardening, monitoring, incident response and automation. GitHub Actions will validate offline policy/detection regression tests; privileged Windows/Containerlab integration tests remain local.

**Deployment status:** planned, **not yet implemented**. The host has approximately 7 GiB RAM, below the recommended host memory for a full Wazuh Docker single-node stack. Feasibility and service co-existence must be measured; phased deployment is allowed and must be documented. No claim is made that AD DS and the complete Wazuh stack currently run together.

See [ESC-002 implementation decision](ARCHITECTURE.md#esc-002-implementation-decision-2026-11-15) and [updated project scope](PROJECT_PLAN.md#esc-002-scope-update-2026-11-15).

## ESM Methodology: Build, Attack, Break, Detect, Fix & Retest

**Build → Attack → Break → Detect → Fix → Retest**

ESM follows an iterative defensive security methodology. Each scenario starts with a functional enterprise environment and documented security controls. We then introduce a controlled weakness, reproduce adversarial behavior in an isolated and authorized lab, investigate the resulting evidence, apply corrective measures and repeat the tests.

The goal is not simply to deploy security tools, but to demonstrate **what they protect, what they detect, where they fail and whether the improvements are effective**. Each scenario documents reproducible tests, evidence, detection limitations and automated regression checks.

The methodology is developed in three complementary layers: **build and observe**, **attack and defend**, and **explore limits and validate**. See the [original project plan](PROJECT_PLAN.md#1-propósito) for the detailed methodology and scope.

## Architecture

- 24 Containerlab nodes: 18 Linux containers and six Open vSwitch bridges.
- 23 topology links.
- A fictional external client (`internet01`) connects through `isp01`, `edge-r01`, `firewall01` and the dedicated DMZ to `web01`.
- The HTTPS portal is published through DNAT: `203.0.113.2:443` to `10.70.50.10:443` (documentation-only addresses).
- A separate corporate core connects HQ user, server, admin and management segments plus three branches via OSPF.
- BOLA audit logs are generated by FastAPI. `detect_bola.py` is an **on-demand log analyzer**, not an always-on SOC sensor.

## Validation

`./scripts/deploy-lab.sh` (run from `infrastructure/containerlab/`) executes the infrastructure policy suite after deployment. The local integration suite is **12 policy checks**, including three expected OSPF neighbors and the HTTPS DMZ health endpoint. Some policy checks use lightweight Netcat listeners for simulated services.

GitHub Actions (`.github/workflows/ci.yml`) runs **offline/static checks and Python tests**; a green CI run does **not** prove that Docker, OVS, OSPF or the HTTPS network path work on another machine.

## Safety and scope

Only run in an isolated, authorized Linux lab. Never publish host ports, bridge this topology to a real company network or use the demonstration credentials elsewhere. HTTPS currently uses an ephemeral, self-signed certificate. Logs and accounts are synthetic; the application is not production-ready.
